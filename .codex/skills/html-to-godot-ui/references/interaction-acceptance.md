# HTML转Godot点击交互测试验收前必读

版本：v0.1  
日期：2026-05-08  
适用范围：所有由 `html_ui/` 原型转换出的 Godot 4.7 原生 2D UI 场景。

本文是点击交互和输入验收前的必读文档。目的不是补样式，而是防止出现“场景能加载、截图也正常，但鼠标点击完全没反应”这类假完成状态。

## 1. 先记住一条红线

`headless` 加载成功，只能证明：

- 场景能实例化。
- 脚本没有立即报错。
- 节点路径大体可用。

`headless` 不能证明：

- 鼠标点击能命中。
- 滑条能拖动。
- 选中态会切换。
- 控件值真的写回状态层。

因此，点击交互验收必须独立执行，不能用加载通过替代。

## 2. 验收范围

每个页面至少覆盖以下输入行为：

- 左键单击。
- 左键按下和抬起反馈。
- hover 高亮或焦点切换。
- selected / focused / pressed 状态切换。
- 可拖动控件的拖拽。
- 底部或侧边按钮的业务动作触发。
- 值变化后是否真实写回控制器或状态对象。

只要其中任一项不通，页面不能标记为“交互完成”。

## 3. Godot 点击交互常见故障点

### 3.1 `mouse_filter` 配置错误

这是最常见的问题。

推荐规则：

- 背景层、纯装饰节点：`MOUSE_FILTER_IGNORE`
- 布局容器、包裹层：`MOUSE_FILTER_PASS`
- 真正可交互的控件：保留命中并处理输入

高风险错误：

- 父容器错误设置成 `IGNORE`，导致整棵子树失去命中机会。
- 装饰层覆盖在按钮上方，却仍然吃掉鼠标。
- 页面根节点或大面板节点使用 `STOP`，让事件无法落到子控件。

## 4. 不要把 `Button.pressed` 当成唯一验收点

复杂 UI 场景中，单靠 `pressed` 不够稳，尤其是：

- 子节点很多。
- 控件内部还有图标、文字、装饰层。
- 包裹层较深。

这类场景推荐同时检查：

- `_gui_input(event)` 是否收到左键按下和抬起。
- `pressed` 信号是否真的触发。
- 子节点是否设置成 `IGNORE`，避免吞事件。

必要时可直接在 `_gui_input(event)` 中接管点击：

- 左键按下：播放短反馈
- 左键抬起：发业务信号

## 5. 选中态不是只有外框亮

HTML 原型里的交互状态通常至少分三层：

- 区域焦点：当前焦点在左导航、右内容区还是底栏
- 行焦点：当前是哪一项被选中
- 控件焦点：这一项内部的控件是否进入活动态

验收时必须分别确认：

- 左侧分类在切出导航区后，是否还错误保持高亮
- 右侧设置行选中后，内部控件是否同步进入 focused 态
- 点击或确认时，是否存在短暂 pressed 反馈

## 6. 拖动控件必须单独验

“能用键盘左右调整”不等于“能鼠标拖动”。

对滑条、进度条、分段控件这类输入项，至少验证：

- 鼠标按下是否命中控件本体
- 拖动时数值是否连续变化
- 松开后数值是否保留
- 值变化是否回传到页面控制器
- 页面重绘后显示值是否一致

如果只改了显示文本，没有把值写回状态层，也算验收失败。

## 7. 推荐验收顺序

1. 先点左侧导航，确认分类切换和高亮逻辑。
2. 再点右侧设置行，确认选中和焦点切换。
3. 再测右侧控件本体：
   - select
   - segmented
   - toggle
   - slider
4. 再测底栏按钮。
5. 最后测键盘与鼠标混用，确认焦点不会乱跳。

## 8. 建议保留的临时调试手段

交互不通时，不要只靠肉眼猜。建议临时加入以下任一项：

- 点击后弹一条 toast，写明收到哪个事件
- 在 `_gui_input` 里打印节点名和事件类型
- 在控制器层打印是否收到业务信号
- 在值写回状态时打印 `setting_id -> value`

调试完成后可以清理，但在问题未钉死前，不要只看截图就宣布完成。

## 9. 页面交互验收清单

- [ ] 左侧可点击区域真实可点
- [ ] 左侧切换后高亮逻辑正确
- [ ] 右侧设置行真实可点
- [ ] 行选中后内部控件状态同步
- [ ] toggle 有点击反馈且值变化正确
- [ ] segmented 可点击具体项
- [ ] slider 可拖动，且值能写回状态层
- [ ] 底栏按钮可点击，且动作正确触发
- [ ] 键盘与鼠标混用后，焦点逻辑仍然正确
- [ ] 不存在“看上去亮了，但业务没执行”的假状态

只要上述任一项未通过，就不能进入最终截图验收。
