# 系统化调试

随意修复会浪费时间并产生新 bug。快速补丁掩盖了根本问题。

**核心原则：** 在尝试修复之前，必须先找到根本原因。修复症状就是失败。

**违反这个流程的字面意思就是违反调试的精神。**

## 铁律

```
没有根本原因调查，就不能修复
```

如果你还没有完成阶段 1，就不能提出修复方案。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产环境中的 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况使用：**
- 时间紧迫时（紧急情况让人想猜测）
- "就一个快速修复"看起来很明显
- 你已经尝试了多个修复
- 之前的修复没有奏效
- 你不完全理解这个问题

**不要跳过：**
- 问题看起来简单时（简单的 bug 也有根本原因）
- 你赶时间时（仓促保证返工）
- 管理者要求立即修复时（系统化比乱试更快）

## 四个阶段

你必须在进入下一阶段之前完成每个阶段。

### 阶段 1：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 注意行号、文件路径、错误代码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 每次都会发生吗？
   - 如果不可复现 --> 收集更多数据，不要猜测

3. **检查最近的变更**
   - 有什么变更可能导致这个问题？
   - Git diff，最近的提交
   - 新依赖，配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI --> 构建 --> 签名，API --> 服务 --> 数据库）：**

   **在提出修复方案之前，添加诊断性插桩：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每一层的状态

   运行一次收集证据，显示在哪里出错
   然后分析证据确定失败的组件
   然后调查那个特定组件
   ```

   **示例（多层系统）：**
   ```bash
   # 层 1：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 层 2：构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 层 3：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 层 4：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪一层失败（secrets --> 工作流 ✓，工作流 --> 构建 ✗）

5. **追踪数据流**

   **当错误深在调用栈中时：**

   参见本目录下的 `root-cause-tracing.md` 了解完整的逆向追踪技术。

   **快速版本：**
   - 坏值从哪里产生？
   - 谁用坏值调用了这个？
   - 持续向上追踪直到找到源头
   - 在源头修复，而不是在症状处

### 阶段 2：模式分析

**修复前先找到模式：**

1. **找到可工作的示例**
   - 在同一代码库中定位类似的可工作代码
   - 有什么与坏掉的类似但能工作的？

2. **与参考实现对比**
   - 如果在实现模式，完整阅读参考实现
   - 不要略读 -- 阅读每一行
   - 应用前完全理解该模式

3. **识别差异**
   - 可工作的和坏掉的之间有什么不同？
   - 列出每一个差异，无论多小
   - 不要假设"那不可能有影响"

4. **理解依赖关系**
   - 这需要哪些其他组件？
   - 需要什么设置、配置、环境？
   - 它做了什么假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清晰陈述："我认为 X 是根本原因，因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做尽可能小的改动来测试假设
   - 一次只改变一个变量
   - 不要同时修复多件事

3. **继续前验证**
   - 有效吗？是 --> 阶段 4
   - 无效？形成新假设
   - 不要在上面叠加更多修复

4. **当你不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 做更多研究

### 阶段 4：实现

**修复根本原因，而不是症状：**

1. **创建失败的测试用例**
   - 最简单的复现方式
   - 尽可能用自动化测试
   - 如果没有框架，用一次性测试脚本
   - 修复前必须有测试
   - 使用 `superpowers:test-driven-development` 技能编写正确的失败测试

2. **实现单一修复**
   - 解决已识别的根本原因
   - 一次只做一个改动
   - 不做"顺手"的改进
   - 不做捆绑的重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有其他测试被破坏？
   - 问题确实解决了？

4. **如果修复不起作用**
   - 停下
   - 计数：你尝试了多少次修复？
   - 如果 < 3：回到阶段 1，用新信息重新分析
   - **如果 >= 3：停下并质疑架构（见下面步骤 5）**
   - 不要在没有架构讨论的情况下尝试第 4 次修复

5. **如果 3+ 次修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每次修复都在不同位置暴露新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实现
   - 每次修复都在其他地方产生新症状

   **停下并质疑基本面：**
   - 这个模式从根本上合理吗？
   - 我们是否在"纯粹靠惯性坚持"？
   - 应该重构架构还是继续修复症状？

   **在尝试更多修复之前与你的人类伙伴讨论**

   这不是失败的假设 -- 这是错误的架构。

## 红线 -- 停下并遵循流程

如果你发现自己在想：
- "先快速修复，之后再调查"
- "就试试改 X 看看行不行"
- "加多个改动，运行测试"
- "跳过测试，我会手动验证"
- "可能是 X，让我修复"
- "我不完全理解但这可能有效"
- "模式说 X 但我会用不同方式适配"
- "主要问题是这些：[列出修复但没有调查]"
- 在追踪数据流之前提出解决方案
- **"再试一次修复"（已经尝试了 2+ 次）**
- **每次修复都在不同位置暴露新问题**

**以上所有情况意味着：停下。回到阶段 1。**

**如果 3+ 次修复失败：** 质疑架构（见阶段 4.5）

## 你的人类伙伴发出的做错了的信号

**注意这些重定向：**
- "那不是在发生吗？" -- 你没有验证就假设了
- "它会给我们展示...吗？" -- 你本应添加证据收集
- "停止猜测" -- 你在不理解的情况下提出修复
- "深度思考" -- 质疑基本面，而不仅仅是症状
- "我们卡住了？"（沮丧） -- 你的方法不起作用

**当你看到这些时：** 停下。回到阶段 1。

## 常见的合理化借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单的问题也有根本原因。流程对简单 bug 也很快。 |
| "紧急情况，没时间走流程" | 系统化调试比猜测-检查的乱试更快。 |
| "先试试这个，再调查" | 第一次修复设定了模式。从一开始就做对。 |
| "确认修复有效后再写测试" | 未测试的修复不会持久。先测试才能证明。 |
| "同时修复多个可以节省时间" | 无法隔离哪个有效。会导致新 bug。 |
| "参考太长了，我会适配模式" | 部分理解保证出 bug。完整阅读。 |
| "我看到问题了，让我修复" | 看到症状 != 理解根本原因。 |
| "再试一次修复"（2+ 次失败后） | 3+ 次失败 = 架构问题。质疑模式，不要再修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|----------|----------|
| **1. 根本原因** | 阅读错误、复现、检查变更、收集证据 | 理解是什么和为什么 |
| **2. 模式** | 找到可工作的示例、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或新假设 |
| **4. 实现** | 创建测试、修复、验证 | Bug 解决，测试通过 |

## 当流程显示"没有根本原因"时

如果系统化调查表明问题确实是环境相关的、时序依赖的或外部的：

1. 你已经完成了流程
2. 记录你调查了什么
3. 实现适当的处理（重试、超时、错误信息）
4. 添加监控/日志以便未来调查

**但是：** 95% 的"没有根本原因"案例是调查不完整。

## 支持技术

这些技术是系统化调试的一部分，在本目录中可用：

- **`root-cause-tracing.md`** - 通过调用栈逆向追踪 bug 以找到原始触发点
- **`defense-in-depth.md`** - 找到根本原因后在多层添加验证
- **`condition-based-waiting.md`** - 用条件轮询替代任意超时

**相关技能：**
- **superpowers:test-driven-development** - 用于创建失败的测试用例（阶段 4，步骤 1）
- **superpowers:verification-before-completion** - 在声称成功前验证修复有效

## 实际影响

来自调试会话的数据：
- 系统化方法：15-30 分钟修复
- 随意修复方法：2-3 小时的乱试
- 首次修复率：95% vs 40%
- 引入的新 bug：接近零 vs 常见
